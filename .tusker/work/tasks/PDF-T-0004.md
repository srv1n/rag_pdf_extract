# PDF-T-0004 · One SC-judgment PDF fails "materialize typed canonical text slices" (1/21) — root-cause to the owning layer + regression

## Intent

Same 2026-07-21 backend ingestion drive as PDF-T-0003: **1 of 21** Supreme Court
judgment PDFs failed `fetch_and_parse` with:

```
Failed to materialize typed canonical text slices
```

Unlike PDF-T-0003 this error message names a downstream step (canonical text-slice
materialization), so the defect may live on either side of the parser boundary:

- **Parser-side hypothesis**: this repo's extraction emits output whose structure
  breaks slice materialization — e.g. empty/degenerate text runs, an offset/length
  inconsistency between extracted text and locator spans, a unit boundary the slicer
  can't type, or an encoding artifact.
- **Backend-side hypothesis**: extraction output is well-formed and the backend's
  slice materializer has an unhandled case.

This task's first job is the **diagnosis that picks the owning layer** — with the
actual document in hand — and its second job is the fix + regression *if* the owner
is this repo. If the owner is the backend, the deliverable is a written handback:
the offending document, the exact structural property of the parser output that
triggers the failure (with a minimal reproducing sample), and which backend
invariant it violates — enough for a backend implementer to fix without re-deriving
the diagnosis.

## Where to find the failing input

- Same corpus + credentials pointers as PDF-T-0003 (R2 `rzn-documents-prod`, prefix
  `tenants/public/sources/70c9e920-…/raw/`; backend `.secrets/e2e/local.env`
  `SOURCE_OBJECT_*` names; dead-letter queue `GET /jobs/dead-letter` on the backend
  serve box holds the failed job payload).
- Identify the document by elimination: 21 PDFs, 2 fail on PDF-T-0003's bbox class;
  this is the remaining failure. Record its filename in the task.
