# PDF-T-0002 · reportlab PDFs return empty_text on backend's pinned pdf-extract (de635f7); current main extracts them — bisect fix + add regression

## Intent

The RZN backend's Phase-1 ingest reported `parse_quality_failed: status=empty_text score=0.00 extracted_chars=0` on reportlab-generated PDFs (3 e2e runs, 2026-06-22, `search-to-card-index-smoke`). Investigation shows this is **NOT a parser bug in current pdf-extract** — it is a **stale version pin**:

- The backend deps pdf-extract via git in `crates/rzn-extract/Cargo.toml` → Cargo.lock pins commit **`de635f7cc694e4398ab51aa2381e2914fc232500`** (v0.7.7). That version produced `extracted_chars=0` on these files in the backend.
- This crate's **current main = `5229e2567a23f5a2231cc3e4bcb751e6ccd582ac`** extracts the same files correctly: `extract_text` and `extract_text_from_mem` both return **667 chars** of correct text.
- Control PDF `tests/docs_cache/embeded-core-fonts.pdf` returns 101,276 chars on current main.

So a fix landed between `de635f7..5229e25`, and the backend is pinned behind it.

**Repro fixtures (in this crate):**
- `tests/fixtures/reportlab_empty_text/reportlab_base14_helvetica.pdf` — base-14 Helvetica, no embedded font / no ToUnicode CMap (1.9 KB)
- `tests/fixtures/reportlab_empty_text/reportlab_embedded_vera.pdf` — embedded DejaVu/Vera TTF + ToUnicode (22 KB)
- `tests/fixtures/reportlab_empty_text/expected_text_excerpt.txt` — expected text
- `tests/fixtures/reportlab_empty_text/generate.py` — reproducible regenerator (needs `reportlab`)
- `examples/rzn_extract_check.rs` — prints char counts via the public entry points

**Reproduce current-main success:**
```bash
cargo run --example rzn_extract_check -- \
  tests/fixtures/reportlab_empty_text/reportlab_base14_helvetica.pdf \
  tests/fixtures/reportlab_empty_text/reportlab_embedded_vera.pdf
# => from_mem: ok chars=667 ; from_path: ok chars=667  (both fixtures)
```

Note: `pdftotext` (poppler) also extracts ~664 chars from these, and real legal PDFs always worked — consistent with current main being correct and only the old pinned commit failing.

## Knowledge delta

The backend↔pdf-extract integration is a **git-pinned dependency**; "parser" symptoms in the backend can be a stale `Cargo.lock` pin rather than a live parser defect. Always compare the backend's pinned pdf-extract commit (`Cargo.lock`) against this crate's `main` before assuming a parser regression.
