# PDF-T-0006 · Constrained-core benchmark variants — 2-core and efficiency-core runs emulating the cloud serve box

## Intent

Production extraction runs on small cloud boxes (currently a 2-vCPU shared-core
Hetzner cx23). The Mac's full-core baseline (PDF-T-0005) doesn't predict that
environment. Add constrained variants of the same benchmark so we know the
parser's honest throughput on weak hardware, and how it scales down:

1. **2-core run** — cap the benchmark to 2 cores (macOS: e.g. run the harness
   with parallelism limited to 2 worker threads; document the exact mechanism —
   thread-pool cap is preferred over OS-level pinning since macOS lacks strict
   CPU affinity).
2. **Efficiency-core run** — schedule the benchmark onto E-cores
   (`taskpolicy -c background` or the documented equivalent) to approximate
   worst-case per-core performance.

Same corpus, same normalized metrics (ms/page, MB/s, chars/s), same report format
as PDF-T-0005 so the three tables (full / 2-core / E-core) read side by side.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | `make bench-corpus-2core` (or a CORES=2 parameter) produces the per-doc table with parallelism provably capped at 2 (mechanism documented in the report). | Inline verification |
| A2 | An E-core variant produces the same table under background/efficiency scheduling, mechanism documented. | Inline verification |
| A3 | A combined report shows full vs 2-core vs E-core aggregates and the scaling ratio (e.g. "2-core ≈ 0.31× full-core throughput"), with a short interpretation: what does this predict for the cx23-class box? | Inline verification |

## Non-goals

- No optimization (PDF-T-0007).
- No Linux-box benchmarking here (the backend's cloud profiling covers that side);
  this task is about a controlled local dial we can iterate on cheaply.
