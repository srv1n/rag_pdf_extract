# PDF-T-0014 · Typed error taxonomy replacing string PDF errors

## Intent

- What this is: replace stringly-typed PDF failures with a typed error enum so callers can programmatically decide retry, OCR fallback, repair, or hard-fail.
- Why it matters: the consuming backend currently pattern-matches error strings to choose behavior; that is brittle and loses information. A typed taxonomy also carries where the failure happened and whether a repair was attempted.
- What "done" looks like: every public entry point returns a typed error distinguishing at minimum not-a-PDF, encrypted, invalid structure, resource limit, parse, and I/O — each carrying phase and page context where known.

## Acceptance

| ID | Outcome | Proof |
|---|---|---|
| A1 | A public error enum distinguishes NotAPdf, Encrypted, InvalidStructure, ResourceLimit, Parse, and Io, with optional phase/page context and a repair-attempted flag. | Automated test |
| A2 | Every public entry point returns it; no `String`-only error remains on the public surface. | Inline verification |
| A3 | Representative fixtures map to the correct variant (non-PDF bytes => NotAPdf, encrypted fixture => Encrypted, truncated => InvalidStructure). | Automated test |
| A4 | Display messages remain human-readable so existing string-logging consumers degrade gracefully. | Automated test |

## Non-goals

- No consumer-side (rzn backend) changes — that repo migrates separately.
- No retryability policy encoded here; callers decide from the variant.

## Implementation notes

- `thiserror` is already a dependency; use it. Audit current error surface in `src/lib.rs` (and `anyhow` usage) first — this is mostly mechanical but wide.
- Coordinate with PDF-T-0010 (owns the ResourceLimit variant semantics) and PDF-T-0016 (owns Encrypted sub-outcomes: missing vs wrong password vs unsupported handler — leave room in the variant).
- Semver: this is a breaking API change; bump minor version (pre-1.0) and note it in MIGRATION.md.
