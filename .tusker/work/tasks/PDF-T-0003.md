# PDF-T-0003 · Negative page-bbox coordinates reject real SC-judgment PDFs (2/21 corpus failures) — normalize coordinates + regression

## Intent

The RZN backend's first live 21-document ingestion drive (2026-07-21, Rung-1 of the
corpus ladder, Indian Supreme Court judgment PDFs) had **2 of 21 documents fail
`fetch_and_parse`** with:

```
pdf_page_bbox.locator.bboxes.{x,y} must be nonnegative
```

Real-world PDFs can carry page boxes with negative origins (MediaBox/CropBox not
anchored at 0,0 — common with scanner/repro output and some court-registry
digitizations). The extraction pipeline currently emits those raw coordinates in its
locator bboxes, and the backend's canonical locator contract rejects negative x/y.
The right fix is almost certainly parser-side: **normalize page-space coordinates so
emitted bbox origins are nonnegative** (translate by the page-box origin, i.e. make
coordinates page-relative), rather than loosening the backend contract — the
nonnegative invariant is what downstream citation/highlight rendering assumes.

If investigation proves the negative values originate in a layer this repo does not
own, the deliverable becomes: the minimal parser-side coordinate-space guarantee,
plus a written handback (exact producing code path, sample values) filed against the
backend.

  the set — the 2 bbox failures are deterministic. Identify them by filename in the
  task record.
